## 🔍 Metodología

1. **Automático / estático**: revisión integral del HTML, CSS y JS (token a token), verificación de estructura semántica, landmarks, headings, alt, ARIA.
2. **Contraste**: cálculo WCAG 2.1 con los hex exactos de `css/tokens.css` y los estilos **computados** del navegador (Chromium) sobre los tres contextos: dark (`#0F1111`/`#292E2D`/`#171A1A`), light (`#F2F1ED`) y mist (`#D8E2DF`).
3. **Comportamiento (teclado)**: skip link (Tab + Enter), orden de tabulación, menú mobile (apertura, cierre con Escape, devolución de foco, trap), foco visible real.
4. **Visual**: reflow a 640 px (≈200 % zoom) y 320 px (≈400 % zoom), screenshots full-page de evidencia.
5. **Consola**: sin errores de consola ni page errors en las 3 páginas.

## 🚨 Hallazgos

### P1-1 — El skip link no mueve el foco al contenido principal (2.4.1 Bypass Blocks)

- **WCAG**: 2.4.1 Bypass Blocks (A)
- **Severidad**: **P1** — el mecanismo de salto no cumple su función para teclado/lectores de pantalla
- **Impacto**: usuario de teclado que activa "Saltar al contenido principal" ve la página desplazada pero **el foco queda en el skip link**; el siguiente Tab vuelve al logo/nav y debe repetir la navegación. El usuario de lector de pantalla no recibe el anuncio del contenido principal como destino de foco (con `tabindex="-1"` el destino debería recibirlo según el patrón esperado).
- **Evidencia** (comportamiento medido en Chromium):
  - Tras `Tab` + `Enter` en el skip link y espera de 600 ms: `activeElement` = `A.skip-link`, `scrollY = 0`, `activeId = ""` (nunca llega a `main#contenido`).
  - Causa: `initSmoothScroll` (`js/main.js:266-280`) intercepta **todos** los `a[href^="#"]` (incluido el skip link `href="#contenido"`, `index.html:38` / `proyectos.html:38` / `contacto.html:38`), hace `e.preventDefault()` y solo ejecuta `target.scrollIntoView({ behavior: 'smooth' })`, que **no mueve el foco**.
- **Fix mínimo** (una línea, en `js/main.js` `initSmoothScroll`): excluir el skip link del interceptor y dejar la navegación nativa por fragmento (el `scroll-padding-top: 72px` de `base.css:15-16` ya cubre el offset del nav fijo):

```js
internalLinks.forEach(function (link) {
  if (link.classList.contains('skip-link')) return; // navegación nativa: mueve foco a #contenido
  link.addEventListener('click', function (e) { ... });
});
```

  Alternativa equivalente si se quiere conservar el smooth scroll en anchors internos: mover el foco explícitamente después del scroll, `target.focus({ preventScroll: true })` cuando el destino tenga `tabindex`.
- **Verificación**: Tab → Enter en skip link → `document.activeElement.id === 'contenido'`; siguiente Tab → primer control del contenido (p. ej. `.btn--primary` del hero), no el nav.

### P1-2 — Al abrir el menú mobile, el foco nunca entra al diálogo modal (APG modal + 2.4.3 Focus Order)

- **WCAG**: 2.4.3 Focus Order (A) / patrón de diálogo modal de WAI-ARIA APG (el `role="dialog"` + `aria-modal="true"` ya declarado en `index.html:70`, `proyectos.html:70`, `contacto.html:70` exige foco dentro del modal al abrir)
- **Severidad**: **P1** — rompe el patrón modal: un usuario que abre el menú y presiona Tab inmediatamente cae al **contenido de fondo** (que además queda operativo bajo un modal `aria-modal`)
- **Evidencia** (comportamiento medido en Chromium, 375 px):
  - `openMenu()` (`js/main.js:23-34`) llama `firstLink.focus()` **sincrónicamente** después de `setAttribute('aria-hidden','false')`, pero `components.css:146-164` define `visibility: hidden` con `transition: opacity 300ms, visibility 300ms` — la `visibility` computada en el momento del `focus()` sigue siendo **`hidden`** (medido con `getComputedStyle`), y `focus()` sobre un elemento `visibility:hidden` **falla silenciosamente**.
  - Estado estable a los 500 ms: menú visible (`visibility: visible`, `opacity: 1`) pero `document.activeElement` sigue siendo el **hamburger**.
  - Primer Tab después de abrir: cae en **"Ver proyectos"** (contenido de fondo), no en el menú. El trap (`main.js:56-76`) solo actúa si el foco está adentro, por lo que nunca se activa al abrir.
- **Fix mínimo** (opción A — JS, un listener): diferir el foco hasta el final de la transición de `visibility`:

```js
function openMenu() {
  hamburger.setAttribute('aria-expanded', 'true');
  mobileMenu.setAttribute('aria-hidden', 'false');
  document.body.style.overflow = 'hidden';
  hamburger.setAttribute('aria-label', 'Cerrar menu de navegacion');
  var focusFirst = function () {
    var firstLink = mobileMenu.querySelector('.nav__mobile-link');
    if (firstLink) firstLink.focus();
  };
  if (mobileMenu.getAnimations().length) {
    mobileMenu.getAnimations().forEach(function (a) { a.finished.then(focusFirst); });
  } else {
    focusFirst();
  }
}
```

  **Fix mínimo (opción B — CSS, más simple y robusta)**: sacar `visibility` de la transición para que `visibility: visible` aplique en el mismo frame que `aria-hidden="false"` (el `opacity` sigue animando):

```css
.nav__mobile-menu {
  /* ... */
  transition: opacity var(--transition-normal);
}
```

  Con B, `firstLink.focus()` funciona sin cambios en JS.
- **Verificación**: abrir el menú → `document.activeElement` debe ser el primer `.nav__mobile-link` ("Inicio"); Tab desde ahí debe wrap dentro del menú (nunca salir al fondo); Escape → foco vuelve al hamburger.

### P2-1 — Borde/fill de los inputs sin contraste mínimo 3:1 (1.4.11 Non-text Contrast)

- **WCAG**: 1.4.11 Non-text Contrast (AA)
- **Severidad**: **P2** — dificulta a usuarios con baja visión identificar los campos del formulario (workaround: labels + placeholder)
- **Evidencia** (cálculo con hex reales + estilos computados; inputs en `contacto.html:95-106`):
  - Borde `1px var(--color-border)` = `rgba(242,241,237,0.12)` (`components.css:481`, token en `tokens.css:79`): blended sobre el fill graphite = `#414544` → **1.42:1** contra el fill y **1.95:1** contra la página negra.
  - Fill `--color-bg-raised` = graphite `#292E2D` contra página `#0F1111` → **1.37:1**.
  - Requerido: ≥ 3:1 para la delimitación visual del componente.
- **Fix mínimo** (en `tokens.css` o directo en `components.css:481`): subir la opacidad del borde. Opciones calculadas:
  - Identidad sage (recomendada): `border: 1px solid rgba(175, 200, 194, 0.7)` → **4.65:1** contra fill / 6.39:1 contra página.
  - Neutra: `border: 1px solid rgba(242, 241, 237, 0.5)` → **4.28:1** / 5.89:1.
- **Verificación**: recálculo del ratio del borde contra el fill del input en dark ≥ 3:1.

### P2-2 — Overflow horizontal de 10 px a 320 px de viewport (1.4.10 Reflow)

- **WCAG**: 1.4.10 Reflow (AA) — a 320 CSS px (≈ 400 % zoom) no debe haber scroll bidireccional ni contenido recortado
- **Severidad**: **P2** — a 400 % de zoom la sección pricing pierde contenido (el `overflow-x: hidden` del body, `base.css:30`, recorta en vez de permitir scroll)
- **Evidencia** (medido en Chromium, viewport 320×800): `scrollWidth = 330` (clientWidth 320); elementos fuera de viewport: `.pricing-card` (width 314, right = 330) y `.btn` (width 275, right = 324). Causa: `.pricing-cards` (`pages.css:835-851`, max-width 420 + margen auto) dentro de `.section` con padding 16 px a ≤ 639 px (`layout.css:59-66`) + `.btn { white-space: nowrap }` (`components.css:203`) que fuerza ancho mínimo del botón "Pedí tu presupuesto".
- **Fix mínimo**: en `/css/layout.css` o `/css/pages.css`, a ≤ 639 px:

```css
.pricing-cards { width: 100%; min-width: 0; }
.btn { white-space: normal; }
```

  (o, alternativamente, reducir el padding lateral del `.section` a 12 px en ≤ 360 px).
- **Verificación**: viewport 320 px → `document.documentElement.scrollWidth === 320` en las 3 páginas.

### P2-4 — Tokens latentes con ratio < AA en contextos light/mist (riesgo de regresión)

- **WCAG**: 1.4.3 Contrast Minimum (AA) — riesgo, **no presente en la práctica hoy**
- **Severidad**: **P2 (latente)** — hoy no se renderizan, pero cualquier uso futuro de `--color-primary`/`--color-error` en light/mist rompe AA sin que se note en diseño
- **Evidencia** (cálculo con hex de `tokens.css`):
  - `.section--mist { --color-primary: #3E6B62 }` (`tokens.css:180-181`): si un `.btn--primary` se usa en mist, texto negro sobre `#3E6B62` = **3.14:1** (FAIL AA, botón de 14 px semibold no es "large text"). Hoy el único primario en mist está dentro de `.pricing-card--featured` que redeclara `--color-primary: sage` (`components.css:918-929`) → OK.
  - `.section--light/mist { --color-error: #B3543F }` (`tokens.css:156,184`): **4.37:1** sobre white y 3.73:1 sobre mist (FAIL AA para texto normal). Hoy los errores del form solo se renderizan en el contexto dark (`#E58E7E` 7.67:1).
- **Fix mínimo** (alinear con la regla del DS "los botones primarios usan sage claro + texto negro en todas partes", `tokens.css:71-75`):
  - En `.section--mist`, devolver `--color-primary: var(--color-sage)` (el botón primario queda sage + `--color-accent-on-primary` negro = 10.7:1) y conservar solo el swap de `--color-accent-ink: #3E6B62` para texto/íconos.
  - Para error en light/mist: oscurecer a `#9E4A36` (**5.33:1** white / **4.55:1** mist) en `tokens.css:156,184`.
- **Verificación**: recalcular ratios de los tokens tras el cambio; escanear si algún `.btn--primary` o `.form-error` cae bajo `.section--light/mist`.

## 📌 Notas P3 (no bloquean AA 2.1)

1. **Progressive enhancement de `.reveal`** (`animations.css:8-13`): si JS falla/bloqueado, el contenido con `.reveal` queda `opacity: 0`. Los lectores de pantalla no se ven afectados (opacity no oculta del árbol de accesibilidad), pero un usuario sin JS perdería el contenido. Recomendación: no aplicar `.reveal` cuando `prefers-reduced-motion` o como fallback `noscript`.
2. **Target size AAA (2.5.5)**: links del footer (`components.css:597-604`) y badges tienen área táctil ≈ 16-18 px. No es requisito AA 2.1; mejora opcional con `padding` en el área clickeable.
